# 영수증 숫자 판별기를 다시 굽는 도구

`public/js/receipt-digits.js`(영수증에 손으로 쓴 숫자를 읽는 망)를 **사장님
장부와 사진으로** 다시 만드는 도구들이다. 평소 돌릴 것이 아니다 — 사장님이
사진을 더 주셨을 때, 또는 표 찾기(`receipt-ocr.js`)를 고쳐서 칸이 달라졌을
때만 돌린다.

사진과 장부는 **저장소에 들어가지 않는다**(사장님 영업 기록이다). 자리를
환경변수로 준다:

```bash
export HG_LEDGER=/어디/엑셀이-있는-폴더     # 한국관 식자재 *.xlsx
export HG_PIX=/어디/사진을-꺼낸-폴더        # 영수증 .jpg
```

## 왜 사람이 정답을 안 적는가

사장님 엑셀이 정답표다. 종이에서 센 줄 수가 엑셀 줄 수와 **맞은** 영수증은
「종이 n째 줄 = 엑셀 n째 줄」이므로, 단가·금액 칸의 글자 수가 엑셀 자리 수와
같으면 글자마다 정답이 붙는다. 2026-10-05 에 사진 13,777장에서 그렇게
17,691자를 모았다 — 사람이 한 자도 안 적었다.

## 순서

```bash
# 1. 압축 파일에서 사진을 꺼내고, 엑셀과 짝이 맞는 것만 남긴다
node tools/match.js                 # picked.tsv 를 만든다
#    (압축을 풀고) node tools/keep.js tmpx allpix

# 2. 사진을 브라우저로 읽어 정답을 붙인다 (탭 8개, 13,777장에 5분)
TABS=8 node tools/harvest.js        # big-paired.bin · big-boot.bin

# 3. 망을 여러 가지 재서 고른다
FOLDS=2 EPOCHS=25 NETS=mlp96,cnn8x64,cnn16x96,cnn24x128 node tools/train.js
node tools/baseline.js              # 예전 방식(가까운 이웃)과 견준다

# 4. 고른 것을 public/js/receipt-digits.js 로 굽는다
KIND=cnn16x96 EPOCHS=25 node tools/bake-net.js

# 5. 끝까지 얼마나 되는지 업체마다 잰다
PER=200 node tools/pervendor.js
```

`big-paired` 는 **치우치지 않은** 정답이고(지금 판별기가 뭐라 읽었는지와
상관없이 모인다) `big-boot` 는 지금 판별기가 맞힌 것만 모인 것이다. **시험은
paired 로만** 하고 boot 는 배울 때만 쓴다. 섞어서 재면 잘 되는 것처럼 보인다.

## 어느 파일이 무엇을 하나

| | |
|---|---|
| `truth.js` | 사장님 엑셀을 「가게\|업체\|날짜」로 읽어 둔다 |
| `match.js` | 사진 이름이 장부와 짝이 맞는 것을 고른다 |
| `keep.js` | 짝이 맞는 사진만 남기고 나머지는 버린다 |
| `harvest.js` | 사진을 브라우저로 읽어 **정답 붙은 숫자 그림**을 모은다 |
| `train.js` | 망을 학습시키고 서로 견준다 (손으로 적은 역전파 — 꾸러미를 안 늘린다) |
| `baseline.js` | 예전 방식(가까운 이웃 + k-means 견본)을 같은 자료로 잰다 |
| `bake-net.js` | 가중치를 int8 로 눌러 `receipt-digits.js` 를 쓴다 |
| `split-vendor.js` | 한 업체 것만 뽑는다 |
| `pervendor.js` | 업체마다 끝까지 얼마나 되는지 잰다 |
| `calibrate2.js` | 업체마다 어느 칸이 단가·금액인지 알아내 본다 (**아직 안 된다**) |
| `rows-to-xlsx.js` | 읽은 줄들을 **사장님 엑셀 양식 그대로** .xlsx 로 만든다 |
| `segloss.js` | **어디서 얼마나 잃는가** — 쪼개기 vs 판별기 |
| `montage.js` | 찾은 선을 사진 위에 그려 눈으로 본다 |
| `gallery.js` | 업체마다 전표 한 장씩 모아 보여 준다 |
| `rows.js` | 한 업체 영수증을 「읽은 값 vs 엑셀」로 찍어 본다 |
| `colkind.js` | 칸마다 글자 모양·채운 비율을 잰다 |
| `harvest-cells.js` | 칸을 **통째로** 배우려고 「칸 그림 + 숫자」를 모은다 |
| `train-seq.js` | 칸을 쪼개지 않고 훑어 읽는 망(CTC) — **아직 지금 방식보다 못하다** |

## 지금 어디까지 되는가 (2026-10-05)

진짜 사진 1,462장(업체 20곳)으로:

| | |
|---|---|
| 표 찾기 | **73%** |
| 칸 가리기 | **58%** |
| 글자 하나 | **88.5%** |
| 한 줄이 다 맞음 | **22%** (房信菓菜行 40% · 韓濟 34%) |

업체 다섯 곳은 **줄 친 표가 아예 없는 전산 출력 전표**다(千宇開發 · 思皓企業社 ·
瑞騰國際 · 阿寶水産 · 龍江興南北商行). 표 찾기로는 영영 안 되고 글줄을 찾는
다른 길이 필요하다 — 대신 기계로 찍은 숫자라 읽기는 훨씬 쉬울 것이다.

## 다음에 손댈 사람에게 — 해보고 안 됐던 것 (2026-10-05)

### 어디서 잃는지는 분명하다

칸 4,609개(단가·금액)를 단계별로 쟀다(`segloss.js`):

| | |
|---|---|
| 글자를 **자리 수대로 쪼갠** 칸 | **46%** |
| 그 중 숫자를 다 맞게 읽은 칸 | 75% |
| 셈으로 고친 뒤 최종으로 맞음 | **38%** |

**쪼개기에서 53.6%, 판별기에서 11.5%** 를 잃는다. 숫자 알아보기를 100% 로
만들어도 칸 정확도는 38% → 46% 밖에 안 된다. **쪼개기가 병목이다.**

### 그런데 쪼개기를 고치는 두 가지가 다 안 됐다

**(1) 칸을 통째로 읽기 (CTC)** — `harvest-cells.js` 로 「칸 그림 + 숫자」
16,723개를 모으고 `train-seq.js` 로 훑어 읽는 망을 학습시켰다. 둘 다 지금
방식(38%)보다 **낮다**:

| | 제일 높았을 때 | 30번 돌린 뒤 |
|---|---|---|
| seq 8×16  | 26.9% (20번) | 26.3% |
| seq 12×24 | **31.4%** (15번) | 29.4% |

- 2자리 43% · 3자리 20% · 4자리 0%. 자리가 늘수록 급히 나빠진다.
- 더 돌리면 **오히려 내려간다**(15번 31.4% → 30번 29.4%). 망을 키우면 조금
  올라가지만 한 시간이 걸린다.
- 걸음을 0.05 보다 키우면 가중치가 NaN 으로 날아간다. 상한을 둬도(0.2·0.6)
  제자리걸음이었다.
- 생각나는 까닭: 순수 SGD 라 CTC 가 느리게 배운다(관성·Adam 이 필요),
  망이 작다, JS 라 돌릴 수 있는 횟수가 적다. **방향이 틀린 것은 아니다** —
  손볼 자리가 남아 있다.

**(2) 쪼개는 길을 여러 가지 만들어 놓고 고르기** — 자리 수를 1~6 으로 놓고
세로 잉크가 얕은 곳을 끊은 가설을 전부 만들어 「수량 × 단가 = 금액」으로
골라 봤다. **22% → 21%** 로 오히려 조금 나빠졌다.

까닭은 분명하다: **가설을 늘려도 고르는 기준이 약하면 소용없다.** 엉뚱한
쪼개기 중에도 셈이 맞아 떨어지는 것이 섞여 들어온다. 업체의 지난 단가
목록을 같이 걸어도 달라지지 않았다.

### 그래서 다음은 **더 센 기준**이다

- **인쇄된 合計.** 전표 여럿에 합계가 찍혀 있다(萬濱·丸邱·泳慶·韓濟·新竹錦·
  鷄蛋 …). 「읽은 금액을 다 더하면 合計와 같은가」는 영수증 한 장을 통째로
  검사한다 — 줄 하나짜리 셈보다 훨씬 세다. **아직 안 해봤다.**
- **업체마다 칸을 사장님이 한 번 눌러 알려주기.** 大川食品行(칸 23%) 같은
  복잡한 양식은 자동으로 못 가린다. 15곳이면 평생 15번이다.
- **전산 출력 전표**(千宇開發·思皓企業社·瑞騰國際·阿寶水産·龍江興南北商行,
  사진 1,828장)는 줄 친 표가 없다. 글줄을 찾는 다른 길이 필요하지만 기계로
  찍은 숫자라 읽기는 훨씬 쉬울 것이다.

## 키 없이 쓰는 길 — 세션에서 읽고 엑셀로 넘긴다 (2026-10-05)

사장님: "api 를 사용하려면 프롬프트를 적어야 하는거고 내가 매번 여기에
넣는거면 그냥 여기에 계속 넣어주면 되는거지?"

그렇다. API 키도 돈도 없이 되는 길이 있다:

1. 사장님이 영수증 사진을 세션에 넣으신다
2. Claude 가 읽어서 JSON 으로 적는다
3. `node tools/rows-to-xlsx.js 읽은것.json` 으로 .xlsx 를 만든다
4. 식자재 탭 「⬆️ 엑셀 가져오기」로 넣으신다

**읽는 품질은 POS 에서 API 로 부르는 것과 같다** — 같은 모델이 같은 사진을
본다. 다른 것은 누가 단추를 누르느냐와 돈이 드느냐뿐이다.

| | 세션에서 | POS 에서 API |
|---|---|---|
| 돈 | 안 듦(구독에 포함) | 한 달 약 $2.5 |
| 누가 | 사장님이 사진을 넣으심 | 직원이 단추만 누름 |
| 품질 | 같음 | 같음 |

`rows-to-xlsx.js` 가 만드는 파일은 가져오기가 **한 줄도 안 흘리고** 받는다
(35줄로 왕복 확인). 머리글은 화면의 `EXPORT_HEAD` 와 한 글자까지 같아야
한다 — 「내  용」의 가운데 공백 둘까지.

## 눈가림으로 재본 것 (2026-10-05)

사진 13,777장에서 무작위로 뽑아, **엑셀을 보기 전에** 사진만 보고 읽어 적고
나중에 맞췄다.

| | 수량·단가·금액 셋 다 | 「확실하다」고 한 줄 |
|---|---|---|
| 1차 — 사진 전체를 1,568점으로 | 26/32 = **81%** | 23/23 = 100% |
| 2차 — **표만 잘라** 1,568점으로 | 35/40 = **88%** | 31/33 = 94% |

1차에서 틀린 여섯 줄을 **확대해 다시 보니 다섯 줄이 읽혔다** — 단가 「90」을
80 으로, 금액 「650」을 610 으로 본 것이 전부 해상도 탓이었다. 그래서 화면이
**표만 잘라 보내고, 줄이 아홉 줄 넘으면 위아래로 갈라** 두 장으로 보낸다
(`cropsForAi`).

**자르기가 품목을 통째로 날릴 수 있다** — 大川食品行 처럼 가로로 긴 전표에서
표를 네 줄로만 찾으면 그 네 줄이 아래쪽 합계 칸인 경우가 있다(12장 중 2장).
그래서 줄이 넉넉하고 사진의 25% 이상을 차지할 때만 자른다.

2차에서 틀린 다섯 줄:
- 阿麵製麵 두 줄은 **종이에 단가가 아예 없다**(사장님이 외워서 적으신다).
  읽어서는 나올 수 없다 — 장부의 지난 단가로 메워야 한다.
- 40 을 45 로, 15 를 55 로 읽은 한 자리 오독 두 줄.
- 도장이 숫자를 덮은 전표 한 줄.
